# 宏槽位返回空鼠标时的处理

## 现场证据

用户提供的正式服 12.1.0 诊断截图中，角色已脱战、鼠标无占用，`PickupAction` 未报告污染来源。动作条槽位 77、78、113、114 的 `GetActionInfo` 返回宏类型，但 `pcall(PickupAction, slot, true)` 成功后 `GetCursorInfo` 没有返回宏；截图中的其他宏槽位可正常读取。

第三条诊断仅输出时间，符合 `Apply:Start` 在捕获当前动作条时提前返回、尚未生成切换记录的代码路径。旧代码对这一返回组合报 `BARS_MACRO_READ`，整次切换在第 77 槽退出。现有证据不能判断这些槽位是残留引用、其他插件创建的动作，还是客户端异常；不把它们当作空槽，也不猜测宏编号。

## 修复行为

- 仅对“复制调用成功且鼠标类型、编号均为空”的宏槽位记录绑定原槽位的 `unreadableMacro` 标记。调用异常、错误类型、无效宏编号、战斗和鼠标占用仍按原有失败处理。
- 恢复时，只要当前槽位或目标记录是该标记，就保留当前槽位，不删除、不覆盖。其余槽位正常恢复并校验；失败时继续执行原有回滚。
- 天赋切换成功后提示保留的槽位编号，诊断记录保留 `BARS_PARTIAL` 和槽位列表。读取恢复正常后，新捕获的布局重新保存确切宏编号。
- 捕获当前动作条的其他失败也写入 `lastAttempt`，包含 `capture-bars` 阶段和失败槽位，不覆盖已有恢复备份。

## 验证与边界

`lua tests/unreadable_macros.lua` 使用上述 API 返回组合调用生产 `Capture`、`Restore`：修复前在第 77 槽失败，修复后覆盖默认/独立布局往返、相同布局无写入、重复宏身份、异常槽位保留、局部恢复回执、正常槽位恢复失败回滚、槽位变为可读后的恢复以及战斗/鼠标保护。

`lua tests/single_config.lua` 覆盖实际 `Apply` 流程完成天赋切换、恢复正常槽位、提示四个保留槽位，以及其他读取失败的槽位记录。

这些是基于现场返回值的离线回归，未在报告问题的用户客户端验证修复。保留槽位的含义是荔枝天赋不改动其恢复阶段看到的内容，不能保证暴雪自身天赋切换或其他插件不会改变该槽位；无法读取的动作也不能声称已按目标布局恢复。
